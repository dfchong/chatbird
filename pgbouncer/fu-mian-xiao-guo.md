# 负面效果

结合你正在 k3s 中为 Go 应用（\`pgxpool\`）部署 PgBouncer 的场景，它的好处和坏处可以很明确地对应到你的实际选择上。\
\
\### 好处：为什么值得引入\
\
大幅缓解连接数压力\
这是最核心的价值。PgBouncer 通过连接复用，让少量后端 PostgreSQL 连接服务大量客户端连接。对于你“多个数据库共享”的场景，它能有效避免每个 Pod 的 `pgxpool` 直接占用数据库连接，防止 `max_connections` 被打满。\
\
资源开销极低\
PgBouncer 非常轻量，默认每个连接仅占用约 2kB 内存。它作为 k3s 中的一个独立服务运行，不会给节点带来明显负担。\
\
部署与集成简单\
单二进制、配置直观，且已有成熟的 Helm Chart 和容器镜像。在 k3s 中通过 Helm 安装只需几分钟，与你现有的 GitOps 或 Helm 工作流能很好地配合。\
\
\### 坏处：你需要付出的代价\
\
单线程架构的硬瓶颈\
PgBouncer 是单线程的。当你的应用并发连接数或事务频率达到一定量级时，PgBouncer 进程自身的 CPU 核心会成为瓶颈，而不是数据库。届时的解法是部署多个 PgBouncer 实例并在前面加负载均衡，这会增加架构复杂度。\
\
\`transaction\` 模式强制应用“无状态化”\
你为了复用效率选择了 `transaction` 模式，这意味着\*\*会话级特性在 PgBouncer 下不可用或行为异常\*\*。官方明确列出了不兼容的特性：\`SET\`（会话级）、\`LISTEN\`、会话级咨询锁、\`WITH HOLD\` 游标、\`PREPARE\` 等。你的 Go 代码必须用 `SET LOCAL` 或 `set_config(..., true)` 来替代普通 \`SET\`，否则会出现会话状态“泄漏”给其他请求的安全隐患。\
\
认证与运维复杂度增加\
\- 认证限制\*\*：如果后端 PostgreSQL 使用 SCRAM 认证，PgBouncer 需要知道明文密码或完全一致的 SCRAM secret。对于托管数据库（如 RDS）禁止读取 \`pg\_authid\` 的情况，配置会变得棘手。\
\- \*\*排错链路变长\*\*：连接问题需要同时排查应用、PgBouncer 和 PostgreSQL 三端日志，比直连多了一层。\
\- \*\*额外组件维护\*\*：你需要监控 PgBouncer 本身的状态（\`SHOW POOLS\` 等），并规划其高可用和升级策略。\
\
\*\*额外网络跳数与延迟\
在 k3s 中，如果 PgBouncer 与你的应用不在同一节点，连接会多一次网络转发，引入微小但存在的延迟。对于延迟极度敏感的服务需要评估这一点。\
\
\### 对你的场景而言\
\
你选择了“多数据库共享” + “`pgxpool` 小池” + “`transaction` 模式”。\*\*好处是\*\* PgBouncer 能在一个地方统一管理所有数据库的连接复用，你的 Go 应用只需维持很小的连接池。\*\*代价是\*\*你必须在代码层面严格遵守 `transaction` 模式的约束（禁用预编译、避免会话状态），并且接受单线程 PgBouncer 在极端并发下的上限。如果当前并发量不高，这些坏处暂时不会显现；但如果未来连接频率激增，就需要提前规划多实例部署。
